**逐工作流结果** `[实测产物]`：

| # | Agent | 名称 | 状态 | 运行状态 | 耗时 | 输出字段 |
|---|---|---|---|---|---|---|
| 1 | `resume` | 档案解析智能体 | ✅ pass | succeeded | 50.69s | `resume_report` |
| 2 | `assessment` | 测评分析智能体 | ✅ pass | succeeded | 40.31s | `assessment_report` |
| 3 | `matching` | 岗位匹配智能体 | ✅ pass | succeeded | 55.73s | `match_report` |
| 4 | `training` | 培训赋能智能体 | ✅ pass | succeeded | 51.17s | `training_report` |
| 5 | `data_decision` | 数据决策智能体 | ✅ pass | succeeded | 49.57s | `structure_result` |

**耗时分析**：单工作流 40–56 秒，平均 **49.5 秒**。耗时主要来自 LLM 生成（qwen3 的 thinking 输出）。

**联调中发现的可改进点（诚实披露）**：

| 现象 | 说明 | 建议 |
|---|---|---|
| 输出含 `<think>` 标记 | 报告预览以 `<think>` 思考过程开头（如测评分析、匹配分析、培训赋能三个 Agent 的输出） | 在 Dify 工作流中关闭 thinking 或增加后处理剥离 |
| 部分 Agent 输入数据为空仍返回"成功" | 如测评分析 Agent 输入 `assessment_result_id=1` 实际不存在，工作流仍 `succeeded` 并生成**模板化/推测性报告**；匹配 Agent 的 `match_results` 为空数组仍生成报告 | 应在工作流中增加数据有效性校验节点，避免"空数据生成看似完整的报告"——**这是 AI 应用的重要可靠性风险** |
| 培训赋能 Agent 输出包含"模拟/虚构"数据 | 因输入为空，模型自行虚构课程与路径 | 同上，须校验输入 |

> **评价**：这 3 点是从实测结果文件中直接读出的真实问题，不是推测。它们的共同根因是"**LLM 工作流缺少输入有效性门禁**"，建议列为迭代改进项。

## 六、集成测试发现的问题

| 编号 | 级别 | 问题 | 影响 | 建议 | 2026-10-15 状态 |
|---|---|---|---|---|---|
| IT-01 | **高** | Dify 工作流缺少**输入有效性门禁**：输入数据不存在时仍返回 `succeeded` 并生成模板化/推测性报告 | 可能输出**看似完整但无依据**的 AI 报告，存在误导决策的风险 | 在 Dify 工作流增加数据校验节点；或后端调用前做前置校验 | ✅ **已修复**（10-13 新增 `_input_gate_passed()`，并补 `data_valid`/`gate` 机器可判定标记） |
| IT-02 | **高** | AI 输出未剥离 `<think>` 标记 | 前端直接展示思考过程，影响专业性与可读性 | Dify 关闭 thinking 或后端后处理剥离 | ✅ **已修复**（10-13 新增 `strip_think_markup()` 并在报告链路全路径应用，6 条用例覆盖） |
| IT-03 | 中 | 用户管理 / 员工自助 / 技能编排 三个模块**无集成测试** | 三个模块的 API 层无自动化回归保障 | 补充集成用例（对应用例评审 R-03） | ⬜ 待办 |
| IT-04 | 中 | 集成测试运行于**内存 SQLite**，未覆盖真实 MySQL 方言差异 | 真实库类型/索引差异未验证（历史已发生枚举存 name 类缺陷） | 增加"真实 DB 联调测试"层 | ⬜ 待办 |
| IT-05 | 中 | 业务数据**结构单一**（389 人全为 reserve 状态、本科占 384） | 看板图表演示效果弱（饼图单扇区）；匹配/统计场景多样性不足 | 补充多状态、多学历、多部门的业务数据 | 🟡 **部分改善**（10-14 新增 `scripts/generate_scale_data.py`，可生成多状态/多学历/多技能的可复现规模数据；实跑待环境） |
| IT-06 | 中 | 无 API 契约测试（响应结构固定性校验） | 接口字段变更可能破坏前端 | 引入响应 schema 断言 | ⬜ 待办 |
| IT-07 | 低 | 无性能断言集成测试 | 集成测试不覆盖延迟 | 结合性能测试补充 | ⬜ 待办 |
| IT-08 | 低 | 独立媒体目录（`demos/`）未随仓库分发 | 证据以交付报告形式承载 | 保留报告为准 | ✅ 已说明 |

## 七、结论

### 7.1 集成测试评价

| 维度 | 评价 |
|---|---|
| 链路连通性 | **优秀**。Dify 5 工作流真实调用 5/5 通过；真实 PDF 简历经 LangGraph + Ollama 端到端建档成功（字段精度 6/6）；数据迁移链路真实跑通；语义检索 hit@1/3 均 100% |
| 降级覆盖 | **优秀**。Milvus/Dify/Vanna 等外部依赖的降级路径均有专门用例（`*_graceful`、`*_missing` 共 8 条），这是本集成测试设计的最大亮点 |
| 空态覆盖 | **良好**。空列表、无数据场景有专门用例 |
| 模块覆盖 | **不均衡**。看板 100%、知识库关键路径完整；但用户管理/员工自助/技能编排三个模块零集成测试 |
| 环境真实性 | **不足**。集成测试基于内存 SQLite，与生产 MySQL 存在方言差异 |
| 证据完备性 | **部分**。Dify 联调有落盘结果 JSON（强证据）；其余为既有记录，建议现场复跑 |

### 7.2 结论

1. **核心业务链路已获真实环境验证**：这是本项目最有说服力的测试证据——不是"跑通了单测"，而是"真实 PDF 简历经完整 AI 链路自动建档成功"、"真实 Dify 中台 5 个工作流全部调用成功"、"真实 MySQL 数据迁移 imported:2/failed:0"。这些是可直接向验收方演示的证据。

2. **降级设计经受住了测试**：8 条降级用例 + 3 条数据缺失用例，验证了系统在依赖不可用时"不崩溃、可降级"的核心健壮性主张。

3. **两类真实 AI 可靠性风险（IT-01、IT-02）已闭环**：
   - **AI 报告在无数据时仍生成内容** —— 这是 AI 应用特有的风险，传统测试方法不易发现，集成测试通过实际调用暴露了它；**已于 2026-10-13 引入输入有效性门禁修复**（无效输入直接拒绝生成，并返回 `gate: input_validation_failed`）；
   - **thinking 标记未剥离** —— 影响输出专业性；**已于 2026-10-13 引入 `strip_think_markup()` 修复**。
   
   两项均由新增单元用例覆盖（见《单元测试报告》3.6 节），回归保障已建立。

4. **三个模块无集成测试**（IT-03）：用户管理、员工自助、技能编排的 API 层缺少自动化回归保障，其中**员工自助是面向普通员工的主入口**，优先级最高。

5. **建议现场复跑以固化证据**：Dify 联调有落盘产物可作为强证据；其余链路建议在验收环境重新执行并留存日志/截图。
