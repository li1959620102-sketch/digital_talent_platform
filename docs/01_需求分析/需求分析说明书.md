## 一、项目背景与建设目标

### 1.1 项目背景

采购人需建设一体化 AI 数字化人才平台，解决当前人才管理中的五类痛点：人才信息零散、能力评估主观、人岗配置低效、培养方向缺失、决策缺乏数据支撑。

平台定位为**企业级 AI 原生数字化人才智能平台**，摒弃传统 HR 表单式系统架构，以大模型 AI Agent 为核心、RAG 知识库为数据底座、AI 工作流编排为业务驱动、自然语言数据分析为决策输出。

### 1.2 建设目标

| 目标维度 | 具体目标 |
|---|---|
| 数字化 | 人才档案全电子化，多源简历智能解析入库 |
| 智能化 | 大模型驱动测评研判、岗位匹配、培训推荐 |
| 精准化 | 人岗双向匹配，输出 0–100 匹配分与可解释依据 |
| 数据化 | 可视化决策看板 + 自然语言问数（NL2SQL） |
| 可控化 | 多级权限、操作留痕、数据不出域 |

### 1.3 业务闭环

```
人才数据采集 → 人才档案 → AI简历解析 → 人才标签/画像
      ↓
AI能力测评 → 岗位分析 → 人才-岗位智能匹配 → 能力缺口分析
      ↓
个性化培训赋能 → 学习考核 → 能力复测 → 人才数据决策
```

## 三、干系人与角色需求

### 3.1 干系人

| 干系人 | 关注点 | 对应系统角色 |
|---|---|---|
| 单位管理层 | 人才结构、流失风险、决策数据 | 浏览决策看板、自然语言问数 |
| HR 部门 | 档案维护、测评组织、招聘匹配 | 人才/测评/匹配/培训主力操作 |
| 系统管理员 | 账号、权限、组织、模型配置 | 全量系统管理 |
| 普通员工 | 个人档案、测评、学习 | 员工自助工作台 |
| 运维人员 | 服务存活、备份、日志 | 运维手册 + 健康检查 |

### 3.2 系统角色定义（实测）

系统内置 4 个系统角色，权限码共 **33 个**（来源：`app/core/rbac.py`）：

| 角色编码 | 角色名称 | 权限定位 |
|---|---|---|
| `super_admin` | 超级管理员 | 全量权限（代码层 `is_superuser` 短路放行） |
| `admin` | 管理员 | 业务全权，含敏感字段明文与薪酬可见 |
| `hr` | HR 专员 | 档案增删改、标签、导入、简历解析、测评管理、匹配执行；**不可删除档案、不可见薪酬** |
| `user` | 普通员工 | **最小权限**：仅 `knowledge:view`（1 个权限）；数据范围 `department`；全字段脱敏；非 staff 用户受"员工自助隔离"约束，仅见本人归属档案 |

## 六、需求变更管理

### 6.1 变更触发条件

出现以下情况必须提出变更：新增功能需求、修改验收指标、修改验收范围、技术栈替换、工期调整。

### 6.2 变更评估维度

每项变更须评估七项：① 影响的功能模块；② 是否影响验收指标；③ 是否影响 4 日验收；④ 工期影响；⑤ 成本影响；⑥ 技术风险；⑦ 备选方案（完整实现 / 简化实现 / 分阶段实现）。

### 6.3 优先级裁决顺序

```
招标/合同验收要求 > 强制技术要求 > 已确认项目决策 > 已批准ADR > 默认方案 > 普通技术建议
```
