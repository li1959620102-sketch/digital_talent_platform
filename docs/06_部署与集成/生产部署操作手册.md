# 生产部署操作手册（全栈上云 · 单台服务器）

> 适用形态：把 9 个容器（MySQL / PostgreSQL / Redis / MinIO / Milvus / etcd / Backend / Ollama / Nginx）
> 整体部署到一台有公网 IP 的云服务器上，通过 HTTPS 对外提供服务。
> 本文只写「怎么做到」，命令均为可直接复制执行。

---

## 0. 部署形态一图说明

```
用户浏览器 ──HTTPS:443──▶ Nginx（唯一对外入口）
                            │
                     proxy_pass /api/
                            ▼
                    FastAPI 后端 :8000
                            │
        ┌───────────────┬───┴────┬────────────┬──────────┐
        ▼               ▼        ▼            ▼          ▼
      MySQL        PostgreSQL   Redis       Milvus     MinIO
     :3306          :5432      :6379      :19530      :9000
                                             │
                                           etcd :2379
                                             
                    Ollama :11434（大模型推理，供后端调用）
```

**关键原则**：只有 Nginx 对公网开放 80/443。其余 8 个服务在 `docker-compose.yml` 里
全部绑定 `127.0.0.1`，天然不对公网暴露 —— 不需要额外改配置，也不要为了「方便」把它们改成
`0.0.0.0`。

## 1. 先过机器规格这一关

9 个容器里最吃资源的是 **Ollama（大模型）与 Milvus（向量库）**，机器规格由它们决定：

| 规格 | 结论 |
|---|---|
| 4 核 8G | ❌ 不可用，Ollama 加载模型时内存不足 |
| **8 核 16G + 100G SSD** | ✅ 最低可用；CPU 推理偏慢（单次简历解析约 60~100 秒） |
| 16 核 32G | ✅ 顺畅，接近生产体验 |

- 操作系统：Ubuntu 22.04 LTS 或 CentOS / 麒麟等均可（架构 x86_64）。
- 安全组 / 防火墙只放行 **22（SSH）、80、443**，不要放行数据库端口。
- 若无公网域名，可先用 `http://公网IP` 验证，再补域名与 HTTPS。

> 若想大幅降低机器规格与成本：可去掉 Ollama 容器，让后端走 SiliconFlow 等云端大模型 API
> （项目已内置 `SILICON_FLOW_API_KEY` 策略与本地 Ollama 自动降级逻辑），此时 4 核 8G 即可。
> 本文按「全栈本地推理」的形态展开。

## 3. 获取代码与配置 .env

```bash
git clone <你的仓库地址> digital_talent_platform
cd digital_talent_platform

# 生成 JWT 密钥
python3 -c "import secrets;print(secrets.token_urlsafe(64))"

# 创建生产环境变量文件
cp .env.example .env
vi .env
```

`.env` 必填项：

| 变量 | 说明 |
|---|---|
| `SECRET_KEY` | 上一步生成的 64 位随机串 |
| `INITIAL_ADMIN_USERNAME` / `INITIAL_ADMIN_PASSWORD` | 首次登录管理员；密码至少 12 位，登录后立即轮换 |
| `AUTH_COOKIE_SECURE` | 已启用 HTTPS 填 `true`；若先用 http 验证，可临时 `false` |
| `CORS_ORIGINS` | 真实前端来源，JSON 数组，如 `["https://talent.example.com"]` |
| `MYSQL_ROOT_PASSWORD` / `POSTGRES_PASSWORD` / `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` / `REDIS_PASSWORD` | 各自独立的强随机值 |

国内服务器**强烈建议**追加两行（构建期依赖源，不影响运行期）：

```
PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
NPM_REGISTRY=https://registry.npmmirror.com
```

> 说明：`docker-compose.yml` 中 `SECRET_KEY`、`CORS_ORIGINS`、`AUTH_COOKIE_SECURE` 等
> 用 `${VAR:?提示}` 强制要求，缺失会直接报错，不会静默用默认值 —— 这是刻意的防呆设计。

## 4. 构建与启动

**务必使用下面的双 `-f` 命令**，它会自动避开本地调试用的 `docker-compose.override.yml`
（该文件会开 `DEBUG=true`、占错端口、绑定本地 media 目录，绝不能带上生产）：

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml config -q   # 先校验
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

也可以直接跑项目自带的脚本（含就绪等待与模型拉取）：

```bash
chmod +x deploy/deploy.sh
```

首次构建会编译后端 Python 依赖 + 前端 npm 依赖（网关镜像内置前端构建阶段），
耗时与网络有关，请耐心等待。构建完成后确认 9 个容器：

```bash
docker ps --filter name=digital_talent --format "table {{.Names}}\t{{.Status}}"
```

预期：`digital_talent_mysql / postgres / redis / etcd / minio / milvus / backend / ollama / nginx`，
其中 mysql/postgres/redis/minio/backend 带 `(healthy)`。

## 5. 首次初始化（模型 / 业务数据 / 向量库）

### 5.1 拉取本地大模型

模型不打进镜像，首次需在服务器上拉取：

```bash
docker exec digital_talent_ollama ollama pull qwen3:1.7b   # 对话模型
docker exec digital_talent_ollama ollama pull bge-m3       # 向量模型（dim=1024）
```

### 5.2 灌业务数据

```bash
docker exec -e PYTHONPATH=/app -w /app digital_talent_backend \
  python -m scripts.seed_midscale_real_data
```

默认生成与交付文档一致的数据基线；如需先清掉旧的种子批次再重灌，加 `--reset-seeded`。
正式生产环境应改为从既有系统批量导入 / 迁移，而非使用种子数据。

### 5.3 灌向量库（三个集合）

```bash
# 人才档案与岗位（幂等：按主键先删后插）
docker exec -e PYTHONPATH=/app -w /app digital_talent_backend \
  python -u scripts/seed_vector_index.py --only both --batch 100

# 知识库分块（先导入文档 → 再由知识库服务切片向量化）
docker exec -e PYTHONPATH=/app -w /app digital_talent_backend \
  python scripts/import_knowledge_base.py --source <制度/课件目录> --destination media/knowledge
```

灌完可用以下方式核对三个集合的实际行数（**不要看 `num_entities`，删除后它会滞后，
要用 `query`**）：

```bash
docker exec -e PYTHONPATH=/app -w /app digital_talent_backend python -c "
from pymilvus import Collection, connections
connections.connect(host='milvus', port='19530')
for n in ['talent_resume','job_position','knowledge_base']:
    c = Collection(n); c.load()
    print(n, len(c.query(expr='id >= 0', output_fields=['id'], limit=5000)))
"
```

### 5.4 启用 HTTPS

项目默认只监听 80。启用 HTTPS 三步：

1. 申请证书（Let's Encrypt 或云厂商免费证书），得到 `fullchain.pem` 与 `privkey.pem`，
   放入 `docker/nginx/ssl/`。
2. 切换 Nginx 站点配置：

   ```bash
   cd docker/nginx/conf.d
   mv default.conf default.conf.disabled
   cp https.conf.example https.conf
   vi https.conf          # 把 talent.example.com 全部替换为真实域名
   ```

3. 按 `docker-compose.prod.yml` 中 nginx 的注释，取消 `ports`（80/443）与 `volumes`
   （含 `./docker/nginx/ssl`）的注释，然后：

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
   docker exec digital_talent_nginx nginx -t
   ```

同时确认 `.env` 中 `AUTH_COOKIE_SECURE=true`、`CORS_ORIGINS` 为 `https://` 域名。

### 5.5 服务器未备案：只能用自签证书（重要）

国内云服务器（阿里云/腾讯云等）如果**域名没有完成 ICP 备案**，80 端口上的 HTTP 服务
会被云厂商的合规网关拦截，表现为返回 `403` 且响应头带 `Server: Beaver`、页面标题为
`Non-compliance ICP Filing`。这会让 Let's Encrypt 的 **HTTP-01 验证必然失败**
（失败原因是 403，不是网络不通，重试无用）。

规避方式有两条：

- **正规做法**：绑定已备案域名 → 完成 ICP 备案 → 再签发证书。
- **过渡做法**：直接用 443 + 自签证书。443 端口不受该拦截影响，实测可正常握手。

  ```bash
  # 容器内已装 openssl，自签证书一步生成（CN 用真实域名，SAN 里带上访问用的 IP）
  docker exec digital_talent_nginx openssl req -x509 -newkey rsa:2048 -nodes \
    -keyout /etc/nginx/ssl/privkey.pem -out /etc/nginx/ssl/fullchain.pem \
    -days 3650 -subj "/CN=<域名>" \
    -addext "subjectAltName=DNS:<域名>,IP:<服务器IP>"
  docker exec digital_talent_nginx nginx -s reload
  ```

  自签证书浏览器会提示"不受信任"，点"继续访问"即可，功能完全正常。正式对外时
  再按上面第一条换成受信任证书。

> 注意：`docker/nginx/conf.d` 是 **bind mount**，改文件名 / `reload` 即生效，
> 不需要重建 nginx 镜像。

## 7. 备份与日常运维

### 7.1 一键定时备份（推荐，脚本已随仓库提供）

`deploy/backup.sh` 按「丢了能不能重建」给数据分级，做了保留策略与日志，
服务器上放到 `/opt/backup.sh` 并挂 cron：

```bash
# 放到服务器并赋权
install -m 755 deploy/backup.sh /opt/backup.sh

# 手动跑一次验证
/opt/backup.sh; echo "退出码=$?"      # 0 表示全部成功

# 每日 03:17 自动执行
(crontab -l 2>/dev/null; echo '17 3 * * * /opt/backup.sh >/dev/null 2>&1') | crontab -
crontab -l
```

备份内容与节奏：

| 对象 | 容器卷 | 节奏 | 保留 | 理由 |
|---|---|---|---|---|
| MySQL 业务库 | — | 每日 | 7 份 | **唯一真相源**，必须每天备 |
| PostgreSQL 分析库 | — | 每日 | 7 份 | 分析看板数据 |
| MinIO 原始文档 | `minio_data` | 每日 | 7 份 | 简历/上传原件，丢了不可重建 |
| 知识库文档目录 | `backend_media` | 每日 | 7 份 | RAG 源文档 |
| Milvus 向量 | `milvus_data` | **每周日** | 3 份 | 可由灌库脚本重建，只做加速 |
| Ollama 模型 | `ollama_data` | 不备份 | — | 2G+ 体积，`ollama pull` 即可恢复 |

产物落在 `/opt/backups/`（实测每日约 11MB，7 天约 77MB），执行日志在 `/var/log/backup.log`。

> **异地留存仍需自行补齐**：本机备份只能防「磁盘坏 / 误删容器」，防不了「整台机器被删」。
> 建议再加一条 `ossutil` / `rclone` 把 `/opt/backups` 同步到对象存储或异地服务器。

**恢复演练**（重要 —— 没验证过的备份等于没有备份）：

```bash
# 先在测试库验证 dump 完整
zcat /opt/backups/mysql_$(date +%F)_*.sql.gz | tail -5
zcat /opt/backups/mysql_$(date +%F)_*.sql.gz | grep -c 'INSERT INTO'

# 真要恢复（会覆盖现有数据，务必先停 backend）
docker compose -f docker-compose.yml -f docker-compose.prod.yml stop backend
gunzip -c /opt/backups/mysql_xxx.sql.gz \
  | docker exec -i digital_talent_mysql sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD"'
docker compose -f docker-compose.yml -f docker-compose.prod.yml start backend
```

### 7.2 手工命令（临时排查用）

```bash
# MySQL 备份
docker exec digital_talent_mysql sh -c \
```

### 7.3 日志轮转（必须开，否则磁盘会被写满）

Docker 默认 `json-file` 驱动**不限制单文件大小**，容器日志只增不减。
`docker-compose.prod.yml` 已通过顶层锚点 `x-log-rotation` 为全部 9 个服务设好上限
（8 个服务 20MB×3，Ollama 因输出频繁单独收紧为 10MB×2，最坏合计约 540MB）。

```bash
# 生效方式：日志驱动是「容器创建时」属性，必须重建容器
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# 验证是否生效
for c in $(docker ps --filter name=digital_talent --format '{{.Names}}'); do
  printf '%-28s ' "$c"
  docker inspect "$c" --format '{{.HostConfig.LogConfig.Type}} {{.HostConfig.LogConfig.Config}}'
done
```

> 重建容器会让业务中断 1~2 分钟（数据在命名卷里不会丢），建议在低峰期执行。
> 同机若还跑着其他项目的容器，`docker compose` 只重建本项目的服务，不影响它们。

## 8. 本项目上云已知坑清单

| 现象 | 原因 | 处理 |
|---|---|---|
| `docker compose build` 卡在 pip/npm 下载或报哈希不匹配 | 服务器连不上官方源 | 在 `.env` 配 `PIP_INDEX_URL`（阿里云）+ `NPM_REGISTRY`（npmmirror） |
| 后端启动即崩、日志提示生产配置不合规 | `AUTH_COOKIE_SECURE` / `CORS_ORIGINS` 不满足生产校验 | 按第 3、5.4 节改 `.env` |
| 简历解析经网关 504，但库里有档案 | AI 接口耗时超过网关读超时 | 已对 AI 接口单独放宽到 600s，见 `default.conf`；确认用的是新配置 |
| Nginx 启动失败 `duplicate upstream` | `default.conf` 与 `https.conf` 同时存在 | 启用 HTTPS 时必须把 `default.conf` 改名为 `.disabled` |
| RAG 问答无结果 | 知识库未向量化 | 走 5.3 节导入并向量化；核对 `knowledge_base` 行数 |
| 向量检索结果为空但库有数据 | Milvus 集合未 load | 服务侧已自动 `load()`；手动核对时也要先 `load()` |
| 登录慢 | 同机 Ollama 占满 CPU | 属资源竞争；可将 AI 推理层与 API 层分离部署 |
| 传 `docker-compose.override.yml` 部署了 | 显式 `-f` 之外被自动加载 | 始终使用第 4 节的双 `-f` 命令 |
| Let's Encrypt 一直报 `timeout / connection refused` | 服务器未备案，80 端口 HTTP 被云厂商拦截（403 + `Server: Beaver`） | 见 5.5 节：先备案，或改用 443 + 自签证书 |
| 4 核 / 8G 小机器上容器反复 OOM 被杀 | Ollama + Milvus + MySQL 同机，内存峰值超限 | 加 swap 兜底（`fallocate -l 8G /swapfile`），或按 8C16G 升配；见 10 节 |
| `scripts/import_knowledge_base.py` 报 `PermissionError` | 用 `docker cp` 灌进 `backend_media` 卷的文件属 root，而容器以 `appuser` 运行 | `docker exec -u root <backend> chown -R appuser:appgroup /app/media` |
| 知识库导入的 `chunks` 统计偏大 | 脚本按 SHA-256 去重，命中已入库文件时会把 `chunk_count` 再累加一次 | 属统计口径问题，数据本身正确；以 MySQL / Milvus 实际行数为准 |

## 10. 实际部署记录（2026-10-16）

本节记录一次真实上云的实测参数与结论，供后续复现或换机时对照。

| 项 | 实测值 |
|---|---|
| 服务器 | 阿里云 ECS，Ubuntu 22.04.5 / x86_64，`47.98.123.164` |
| 规格 | **4 核 / 7.3 GB / 40 GB 磁盘**（低于本文建议的 8C16G） |
| 部署目录 | `/opt/digital_talent_platform` |
| 对外入口 | `https://47.98.123.164/`（自签证书，CN=`47.98.123.164.sslip.io`） |
| 运行结果 | 9 个容器全部 Up，`backend` healthy |

实测结论（与本文前面的建议不同，以实测为准）：

1. **4 核 / 8G 能跑起来，但必须加 swap。** Ollama + Milvus + MySQL 同机时内存峰值会触顶，
   已加 8G swap（`vm.swappiness=10`）兜底后 9 容器稳定运行。长期运行建议升配到 8C16G。
   磁盘 40G 偏紧：镜像约 14G + Ollama 模型 2.6G，灌完业务数据与向量后仍有约 5G 余量。
2. **80 端口确实被拦截，443 畅通。** 该机未备案，`http://` 一律返回
   `Non-compliance ICP Filing`，因此直接走 5.5 节的自签证书方案。
3. **服务器上构建不需要换源。** apt / pip / npm（npmmirror）全部可达，
   `.env` 里的 `PIP_INDEX_URL` / `NPM_REGISTRY` 保持默认即可。
   镜像拉取若官方源慢，可改用 `docker.m.daocloud.io` 前缀。
4. **向量灌库耗时与 CPU 强相关。** 本机约 20 分钟跑完 1320 条；4 核服务器上
   `--batch 100` 时约 100 条 / 100 秒，整体 25 分钟左右。建议放后台跑并写日志：
   ```bash
   nohup docker exec digital_talent_backend \
     python -u -m scripts.seed_vector_index --only both --batch 100 \
     > /opt/seed_vec.log 2>&1 </dev/null & disown
   ```
5. **`backend_media` 是命名卷，内容不会随 `docker cp` 自动对齐属主。**
   把宿主机文件灌进卷之后必须 `chown -R appuser:appgroup /app/media`，否则知识库导入会
   报 `PermissionError`（见第 8 节）。
6. **网关只代理 `/api/`。** `/health` 这类根级路径在 443 上会落到前端 SPA 的
   `try_files` 兜底、返回 HTML 而不是 JSON。对外探活请用 `/api/v1/...` 接口，
   容器级探活走 `docker exec` 调容器内的 `/health`（Docker healthcheck 即如此）。
- 本文是**面向「拿到服务器后照着做」的可执行操作手册**，与上述文档互为补充。
