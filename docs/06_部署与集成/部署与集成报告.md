### DEP-05 说明：为什么**没有**启用多 worker

表面看"注入 `WORKERS=4`"是性能优化，但本应用存在**进程内单例状态**：

- `SkillRegistry`（技能组件注册表）、`PipelineStore`（技能编排存储）均为**内存态单例**（见 `app/services/skill_engine.py`）；
- LangGraph checkpointer 在无 Redis 时降级为 `MemorySaver`（进程内）。

若启用多 worker，用户在 worker A 创建的技能编排在 worker B 不可见，表现为"编排时有时无"。因此**保持单进程是正确的工程选择**。若确需多 worker，须先完成：

1. `skills` 编排持久化到数据库（替换内存 `PipelineStore`）；
2. 确保 Redis 可用，使 checkpointer 走 `RedisSaver` 跨进程持久化；
3. 而后将 Dockerfile 的 `CMD` 改为 `--workers 4` 并复测。

> 注：`config.WORKERS` 仅作用于 `main.py` 的 `__main__` 直接运行分支；Dockerfile 的 `CMD` 是显式 `uvicorn main:app --host 0.0.0.0 --port 8000`，不读该配置。

### 2.3 后端镜像（`backend/Dockerfile`，2026-10-14 加固后实测）

```dockerfile
FROM python:3.11-slim
WORKDIR /app

# 仅安装运行期所需的系统依赖
RUN sed -i 's|http://deb.debian.org|https://deb.debian.org|g' /etc/apt/sources.list.d/debian.sources \
    && apt-get -o Acquire::Retries=5 update \
    && apt-get -o Acquire::Retries=5 install -y --no-install-recommends \
    tesseract-ocr tesseract-ocr-chi-sim \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir --retries 8 --timeout 180 -r requirements.txt

COPY . .

# 非 root 运行，降低容器逃逸后的权限风险
RUN addgroup --system appgroup \
    && adduser --system --ingroup appgroup appuser \
    && mkdir -p logs media \
    && chown -R appuser:appgroup /app
USER appuser

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", \
     "--proxy-headers", "--forwarded-allow-ips", "*"]
```

**镜像设计说明（10-14 加固要点）**：

| 项 | 设计 | 原因 |
|---|---|---|
| **非 root 用户** | 创建 `appuser`/`appgroup` 并 `USER appuser` | 容器逃逸后权限受限，符合最小权限原则 |
| **无编译器** | 未安装 gcc/g++；Python 包全用预编译 wheel | 减小镜像体积与攻击面；`requirements.txt` 已锁定 wheel 可用版本 |
| **系统依赖极简** | 仅 `tesseract-ocr` + `tesseract-ocr-chi-sim`（中文 OCR） | 图片简历解析需要；其余处理（PDF/Word）由纯 Python 包完成 |
| **apt 重试** | `Acquire::Retries=5`、apt 源改 HTTPS | 提升构建稳定性 |
| **pip 重试** | `--retries 8 --timeout 180` | 弱网/镜像源波动下减少构建失败 |
| **测试依赖隔离** | 生产仅装 `requirements.txt`；pytest/pytest-cov 在 `requirements-dev.txt` | 测试工具不进生产镜像 |
| **密钥不入镜像** | 配合 `backend/.dockerignore` 排除 `.env` | 防止密钥随镜像层外泄 |

**基础镜像选型**：`python:3.11-slim` 为**官方多架构镜像**，因此**无需修改 Dockerfile 即可构建 arm64 版本**——这是国产化方案能低成本落地的关键前提。

### 2.4 网关配置（`docker/nginx/conf.d/default.conf`，实测）

| 配置项 | 值 |
|---|---|
| upstream | `backend_upstream → backend:8000`，`keepalive 32` |
| 监听 | 80 |
| 前端根目录 | `/usr/share/nginx/html` |
| API 代理 | `location /api/` → `proxy_pass http://backend_upstream` |
| 代理头 | `Host` / `X-Real-IP` / `X-Forwarded-For` / `X-Forwarded-Proto` / `Connection ""` |
| **大文件上传** | `client_max_body_size 50m`（对应 `MAX_UPLOAD_SIZE=52428800`） |
| 请求缓冲 | `proxy_request_buffering off` |
| 超时 | `proxy_read_timeout 300s` / `proxy_send_timeout 300s` |
| **SPA 回退** | `try_files $uri $uri/ /index.html` |
| **版本隐藏** | `server_tokens off`（不泄露 Nginx 版本号） |
| **安全响应头** | `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy: camera=(), microphone=(), geolocation=()` |
| **登录限流** | `limit_req_zone $binary_remote_addr zone=login_limit:10m rate=10r/m`；`location = /api/v1/auth/login` 配 `burst=5 nodelay` |
| **响应压缩** | `gzip on`（json/css/js/xml 等） |

**设计要点**：
1. `proxy_read_timeout 300s` 是为 **AI 长任务**准备的——Dify 工作流实测耗时 40–56 秒，默认 60s 超时会中断请求。300s 提供了充足余量。
2. **登录限流落在网关层**：每个来源 IP 每分钟最多 10 次登录请求、突发最多放行 5 个。应用层未注册限流中间件（见《交付文档总览》D-05），因此**部署时 Nginx 是限流的唯一执行点**，不可省略。
3. `X-Frame-Options: DENY` + `nosniff` + `Referrer-Policy` 三项安全头为 10-14 新增，用于防御点击劫持、MIME 嗅探与 Referer 泄露。

### 3.3 启动初始化流程（`main.py` lifespan，实测）

```
① 创建目录（MEDIA_ROOT / logs）
② init_db()           → MySQL 同步/异步引擎 + PgSQL 异步引擎（延迟初始化）
③ init_redis()        → 3 次重试，失败降级 None 但不阻塞
```

## 四、部署配置缺陷（原为阻断级 —— **已于 2026-10-13 全部修复**）

> 本节保留缺陷的原始分析（含根因与修复方案），便于回溯与复用。
> **当前状态：DEP-01 / DEP-02 / DEP-02b / DEP-03 / DEP-06 / DEP-07 均已修复，
> `docker compose config --quiet` 校验通过（退出码 0）。详见文首「修复记录」。**

本次逐行核对 `docker-compose.yml` 发现**两处会导致全栈部署失败或错连的缺陷**。这是本报告最重要的发现。

### 缺陷 1：`milvus` 依赖未定义的服务 `minio`（**阻断性**）

**问题**：

```yaml
  # minio 服务块已被整体注释（第 68–84 行）
  # minio:
  #   image: minio/minio:latest
  #   ...

  milvus:
    image: milvusdb/milvus:v2.4.0
    depends_on:
      - etcd
      - minio          # ← 引用了被注释掉的服务
```

**影响**：执行 `docker compose up -d` 时，Docker Compose 会校验依赖图并**直接报错终止**：

```
service "milvus" depends on undefined service "minio": invalid compose project
```

**即：全栈一键部署当前无法启动。**

**修复方案（二选一）**：

```yaml
# 方案 A（推荐）：从 depends_on 中移除 minio
  milvus:
    depends_on:
      - etcd

# 方案 B：恢复 minio 服务定义（若确需独立 MinIO）
  minio:
    image: minio/minio:latest
    container_name: digital_talent_minio
    restart: always
    environment:
      MINIO_ACCESS_KEY: minioadmin
      MINIO_SECRET_KEY: minioadmin
    ports:
      - "9100:9000"
      - "9101:9001"
    volumes:
      - minio_data:/minio_data
    command: minio server /minio_data --console-address ":9001"
    networks:
      - digital_talent_network
```

> **建议采用方案 A**：注释中已说明复用 `milvus-minio` 容器（宿主机 9100=API / 9101=Console），无需独立 MinIO。

### 缺陷 2：后端数据库环境变量名与配置类不匹配

**问题**：`docker-compose.yml` 的 backend 服务注入的环境变量名与 `app/core/config.py` 的字段名不一致：

| compose 注入的变量 | config.py 期望的字段 | 是否匹配 |
|---|---|---|
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` | `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` | ✅ 匹配 |
| **`MYSQL_DB`** = `digital_talent` | **`MYSQL_DATABASE`** | ❌ **不匹配** |
| `POSTGRES_HOST` / `POSTGRES_PORT` / `POSTGRES_USER` / `POSTGRES_PASSWORD` | 同名 | ✅ 匹配 |
| **`POSTGRES_DB`** = `digital_talent_analytics` | **`POSTGRES_DATABASE`** | ❌ **不匹配** |
| `REDIS_HOST` / `REDIS_PORT` | 同名 | ✅ 匹配 |
| `MILVUS_HOST` / `MILVUS_PORT` | 同名 | ✅ 匹配 |
| `OLLAMA_BASE_URL` | 同名 | ✅ 匹配 |

**影响分析**：

`Settings` 配置了 `extra="allow"`，因此 `MYSQL_DB` / `POSTGRES_DB` 这两个**未知变量会被静默忽略**，应用将回退到 `config.py` 的默认值：

| 变量 | compose 意图 | 实际生效（默认值） | 后果 |
|---|---|---|---|
| MySQL 库名 | `digital_talent` | `digital_talent`（默认值） | ✅ **巧合一致，无影响** |
| PostgreSQL 库名 | `digital_talent_analytics` | **`talent_analytics`**（默认值） | ❌ **库名不匹配** |

而 `docker-compose.yml` 中 PostgreSQL 服务创建的是 `digital_talent_analytics`：

```yaml
  postgres:
    environment:
      POSTGRES_DB: digital_talent_analytics      # ← 容器里建的是这个库
```

**后果**：全栈部署时后端会尝试连接不存在的 `talent_analytics` 库，**PostgreSQL 连接失败 → 分析库初始化失败**（因降级设计不会阻断应用启动，但分析类功能不可用）。

**修复方案**：

```yaml
# docker-compose.yml 的 backend.environment 中，改为：
      - MYSQL_DATABASE=digital_talent
      - POSTGRES_DATABASE=digital_talent_analytics
```

> **提示**：这也解释了为何项目采用 `docker-compose.dev.yml`（核心 3 服务）+ 本机直跑后端的方式进行开发验证——该路径下 `.env` 直接生效，绕开了上述不匹配问题。

### 4.3 其他建议修复项

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 3 | `backend` 服务未注入 `PORT` / `WORKERS` 环境变量 | 容器内固定 1 worker，未启用多进程 | 增加 `- WORKERS=4`；或 CMD 改为 `--workers 4` |
| 4 | `backend` 服务未注入 `SECRET_KEY` | 容器内使用默认弱密钥（`your-secret-key-change-in-production`） | **生产必须注入强随机 SECRET_KEY**（安全风险） |
| 5 | `backend` 服务未注入 `EMBEDDING_DIM` | 依赖代码默认值 1024（当前 OK） | 显式注入，防止默认值变更导致向量集合异常 |
| 6 | `backend` 挂载 `./backend:/app` 覆盖镜像代码 | 生产环境应用镜像内代码而非挂载源码 | 生产移除该 volume |
| 7 | `nginx` 挂载 `./docker/nginx/ssl` 但无证书文件 | HTTPS 不可用（仅 80 生效） | 补充证书或移除 443 监听 |
| 8 | 未注入 `DIFY_*` 系列变量 | 容器内 Dify 集成默认关闭 | 需要时注入 |
| 9 | `mysql` 服务未挂载自定义 `my.cnf` 调优 | 默认参数，高并发下可能不足 | 按需调优 |

1. **部署编排设计完整，且已完成安全加固**：9 服务 compose 覆盖数据层、AI 层、应用层、网关层；Dockerfile 已改为**非 root 运行 + 无编译器 + 运行期/测试依赖分离**；Nginx 已补**版本隐藏、4 项安全响应头与登录限流**，并针对 AI 长任务做了 300s 超时调整；应用侧新增**生产配置强校验**、生产关闭 Swagger。Dockerfile 系统依赖仍保留中文 OCR 引擎 `tesseract-ocr-chi-sim`。

2. **全栈一键部署的阻断项已修复**（DEP-01）：`milvus.depends_on` 引用的 `minio` 服务定义已恢复，`docker compose config --quiet` 退出码 0；反证测试确认原写法报 `depends on undefined service "minio"`。**配置层面已可一键部署**，实跑验证（DEP-10）仍待执行。

3. **数据库连接错配已修复**（DEP-02）：`MYSQL_DB` / `POSTGRES_DB` 已改为 `config.py` 期望的 `MYSQL_DATABASE` / `POSTGRES_DATABASE`；backend 亦补齐 `MINIO_*` 注入，容器内不再回退到 `localhost:9100`（DEP-02b）。

4. **已验证的集成链路扎实**：真实 PDF 简历端到端建档（字段精度 6/6）、Dify 5 工作流 5/5 通过、数据迁移 imported:2/failed:0、语义检索 hit@1/3 均 100%——这些真实环境证据比配置核对更有说服力。

5. **性能达标情况需如实陈述**：核心业务接口（读 4–46ms、写 36–48ms、50 并发 0 失败）达标；但**登录 ≤1s、向量检索 ≤500ms、2000 并发**三项受本机 CPU 算力约束，属容量/硬件约束而非代码缺陷，需生产 GPU + 分离部署后复测。

6. **降级设计是系统可用性的关键保障**：Redis/Milvus/Ollama/Dify 四类依赖均有降级路径且不阻塞启动，这在容器编排启动顺序不确定的场景下尤为重要。
