# AI数字化人才平台 — 向量库与数据库设计

> 阶段：第二阶段（设计文档）
> 版本：v1.1 ｜ 编制日期：2026-09-16 ｜ 最近修订：2026-10-15
> 设计原则：**四库协同、各司其职、数据互通**；禁止单一数据库包揽全部业务
> 数据来源：`app/models/*.py`（21 张 ORM 表）、`docker/mysql/init/01_init.sql`、`docker/postgres/init/01_init.sql`、`app/core/milvus_client.py`、`app/core/config.py`

---

## 一、四库混合存储总览

| 数据库 | 版本 | 存储内容 | 定位 | 实测规模 |
|---|---|---|---|---|
| **MySQL** | 8.0 | 组织、用户、角色权限、岗位、人才档案、测评、培训、知识元数据、审计日志 | 核心业务交易库（高频读写、强一致） | **21 张表** |
| **PostgreSQL** | 15 | 人才年度台账、测评历史、培训轨迹、行为时序 | 海量分析与时序库（复杂统计、多维分析） | **4 张表**（schema `analytics`） |
| **Milvus** | 2.4.0 | 人才简历向量、岗位需求向量、知识库文本向量 | 向量检索专属库（语义检索、RAG、智能匹配） | **3 个集合**，dim=1024 |
| **Redis** | 7 | 热点缓存、会话、Agent 记忆、限流计数、实时统计 | 缓存与实时计算中间件 | — |
| **MinIO** | — | 简历文件、知识文档对象存储 | 对象存储（持久化副本） | bucket `resumes` |

**字符集**：MySQL 全库 `utf8mb4` / `utf8mb4_unicode_ci`（支持中文与 emoji）。

#### 2.1.8 `data_permissions`（数据权限表）

| 字段 | 类型 | 说明 |

**配套前提**：部门级过滤依赖 `talents.department_id` 有值。历史业务数据中该字段大量为 NULL，需通过 `scripts/generate_scale_data.py` 或业务导入补齐部门归属，`user` 才能看到本部门记录（见 DB-01/DB-02）。

### 2.2 人才档案域（1 张表）

#### `talents`（人才档案表）

| 字段组 | 字段 | 类型 | 约束/默认 | 说明 |
|---|---|---|---|---|
| 标识 | `id` | INT | PK | — |
| | `talent_code` | VARCHAR(50) | NOT NULL, UNIQUE, INDEX | 人才编号 |
| | `name` | VARCHAR(50) | NOT NULL, INDEX | 姓名 |
| 基本信息 | `gender` | ENUM('male','female') | NOT NULL | 性别（存 value 非 name） |
| | `birth_date` | DATE | NULL | 出生日期 |
| | `id_card` | VARCHAR(18) | NULL | 身份证号（**字段级权限保护**） |
| | `phone` | VARCHAR(20) | NOT NULL, INDEX | 手机号（**字段级权限保护**） |
| | `email` | VARCHAR(100) | NULL | 邮箱（**字段级权限保护**） |
| | `address` | VARCHAR(200) | NULL | 地址（**字段级权限保护**） |
| 教育 | `education` | ENUM('高中','大专','本科','硕士','博士') | NULL, INDEX | 最高学历（**中文值存储**） |
| | `major` | VARCHAR(100) | NULL | 专业 |
| | `education_records` | JSON | DEFAULT [] | 教育背景列表 |
| 工作 | `experience_years` | INT | DEFAULT 0, INDEX | 工作年限（匹配算法输入） |
| | `current_company` | VARCHAR(100) | NULL | 当前公司 |
| | `current_position` | VARCHAR(100) | NULL | 当前职位 |
| | `work_experiences` | JSON | DEFAULT [] | 工作经历列表 |
| 技能 | `skills_certificates` | JSON | DEFAULT [] | 技能证书列表（**匹配算法核心输入**） |
| 期望 | `expected_salary_min` / `_max` | INT | NULL | 期望薪资（**字段级权限保护，无权限置 null**） |
| | `expected_position` | VARCHAR(100) | NULL | 期望职位 |
| 其他 | `self_introduction` | TEXT | NULL | 自我介绍 |
| | `status` | ENUM('active','reserve','resigned','on_leave') | DEFAULT 'reserve' | 状态 |
| 归属 | `department_id` | INT | FK→organizations, SET NULL | 所属部门 |
| | `user_id` | INT | FK→users, INDEX | **归属用户（员工自助隔离依据）** |
| 画像 | `tags` | JSON | DEFAULT [] | 标签列表 |
| | `portrait` | JSON | NULL | 人才画像 |
| | `capability_rating` | JSON | NULL | 能力评级 |
| 简历 | `resume_file_id` | VARCHAR(128) | NULL | 简历文件 ID |
| | `resume_file_name` | VARCHAR(512) | NULL | 简历文件名 |
| | `is_parsed` | BOOLEAN | DEFAULT FALSE | 是否已解析 |
| 时间 | `created_at` / `updated_at` | DATETIME | server_default NOW() | `updated_at` 带 `onupdate` |

**索引（6 个）**：`idx_talent_code`、`idx_talent_name`、`idx_talent_phone`、`idx_talent_status`、`idx_talent_department`、`idx_talent_education`、`idx_talent_experience`

**关键设计说明**：
1. **枚举存值不存名**：`gender` / `education` / `status` 使用 `Enum(..., values_callable=lambda e: [m.value for m in e])`，确保数据库存的是 `male`/`本科` 而非 `GenderEnum.MALE`。这是**已修复的重要缺陷**（历史 BUG：SQLAlchemy 默认存枚举名，导致数据不可读）。
2. **标签与画像用 JSON 而非关联表**：原设计有 `talent_tags` / `talent_tag_relations` 两张表，因前后端均未使用已移除，改用 `talents.tags` JSON 字段（更简洁，足以覆盖演示场景）。代码中保留注释备将来启用。
3. **`user_id` 隔离设计**：HR 录入的人才档案 `user_id` 为空（全局人才池）；员工自助上传的档案绑定 `users.id`（个人档案）。行级权限据此实现隔离。

## 四、Milvus 向量库设计

### 4.1 集合总览

| 集合名 | 用途 | 主键 | 向量维度 | 索引 | 度量 |
|---|---|---|---|---|---|
| `talent_resume` | 人才简历语义检索、人才查重、语义化人才搜索 | `id` INT64 auto_id | 1024 | HNSW | COSINE |
| `job_position` | 岗位语义检索、岗位描述向量 | `id` INT64 auto_id | 1024 | HNSW | COSINE |
| `knowledge_base` | RAG 知识库检索 | `id` INT64 auto_id | 1024 | HNSW | COSINE |

**统一索引参数**：

```json
{ "metric_type": "COSINE", "index_type": "HNSW", "params": { "M": 16, "efConstruction": 256 } }
```

**检索参数**：`{"metric_type": "COSINE", "params": {"ef": 64}}`

**向量模型**：`bge-m3:latest`（Ollama 本地推理），维度 **1024**（由 `EMBEDDING_DIM` 配置控制）。

### 4.2 集合 1：`talent_resume`（人才简历向量）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INT64 | PRIMARY, auto_id | Milvus 自动分配 |
| `embedding` | FLOAT_VECTOR | dim=1024 | 简历文本向量 |
| `talent_id` | VARCHAR(64) | — | MySQL `talents.id`（**关联键**） |
| `resume_text` | VARCHAR(65535) | — | 简历切片文本 |
| `chunk_id` | VARCHAR(128) | — | 切片 ID |
| `file_id` | VARCHAR(128) | — | 文件 ID |
| `file_name` | VARCHAR(512) | — | 文件名 |
| `business_scene` | VARCHAR(128) | — | 业务场景标记：`talent_resume` |
| `created_at` | INT64 | — | Unix 时间戳 |

**写入约定**：调用 `MilvusService.insert(embeddings, metadata_list)` 时，`metadata_list` 的元素**不得包含 `embedding` 字段**（内部已拼入），否则抛 `DataNotMatchException`。

### 4.3 集合 2：`job_position`（岗位需求向量）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INT64 | PRIMARY, auto_id | — |
| `embedding` | FLOAT_VECTOR | dim=1024 | 岗位 JD 向量 |
| `position_id` | VARCHAR(64) | — | MySQL `job_positions.id`（**关联键**） |
| `position_text` | VARCHAR(65535) | — | 岗位描述文本 |
| `position_name` | VARCHAR(256) | — | 岗位名称 |
| `department` | VARCHAR(256) | — | 部门（**支持标量过滤**） |
| `business_scene` | VARCHAR(128) | — | 业务场景标记：`job_position` |
| `created_at` | INT64 | — | Unix 时间戳 |

**更新策略**：`update_job_position_vector()` 采用"**先按 `position_id` 删除旧向量，再插入新向量**"（Milvus 不支持原地更新）。

**标量过滤示例**：`department == '3'`（通过 `expr` 参数传入）。

### 4.4 集合 3：`knowledge_base`（知识库向量）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INT64 | PRIMARY, auto_id | — |
| `embedding` | FLOAT_VECTOR | dim=1024 | 知识切片向量 |
| `knowledge_text` | VARCHAR(65535) | — | 切片文本 |
| `knowledge_type` | VARCHAR(128) | — | 知识类型 |
| `file_id` | VARCHAR(128) | — | 关联 `knowledge_files.id` |
| `file_name` | VARCHAR(512) | — | 文件名 |
| `chunk_id` | VARCHAR(128) | — | 关联 `knowledge_chunks.chunk_code` |
| `business_scene` | VARCHAR(128) | — | 业务场景标记 |
| **`permission_level`** | INT64 | — | **权限级别（RAG 权限过滤依据）** |
| `created_at` | INT64 | — | Unix 时间戳 |

**权限过滤设计**：检索时通过 `expr` 参数过滤 `permission_level`，实现"不同角色只能检索权限内内容"。**权限过滤在检索前执行**，避免越权内容进入 LLM 上下文。

### 4.5 向量检索性能设计

| 设计点 | 说明 |
|---|---|
| 索引选择 | HNSW（图索引）相比 IVF_FLAT 在中小规模数据集上召回率更高、延迟更低 |
| `M=16` | 每个节点的最大连接数，平衡精度与内存 |
| `efConstruction=256` | 建索引时的候选集大小，提升索引质量 |
| `ef=64` | 检索时候选集大小，平衡召回与延迟 |
| 懒连接 | `MilvusService.__init__` 检查连接存在性，未连接则补建，规避启动时序问题 |
| schema 校验 | `ensure_schema()` 对比字段集合，防止 schema 漂移导致 insert/search **静默失败** |
| 写入健壮性 | 批量 3 次重试 → 全失败降级逐条插入，单条失败不中断 |
| 检索兼容 | 兼容 PyMilvus 2.x (`hit.entity.fields`) 与 3.x (`hit.fields`) |

**实测性能**：向量检索 P50 ≈ 482ms / P95 ≈ 583ms（含查询 embedding 生成）。Milvus 本身检索 <100ms，**延迟主要来自 Ollama embedding 的 CPU 推理**。招标要求 ≤500ms，CPU 环境下接近边界，GPU 环境 `[待验证]` 达标。

## 五、Redis 缓存设计

### 5.1 用途划分

| 用途 | 说明 |
|---|---|
| 热点数据缓存 | 高频访问的人才、岗位等数据 |
| 用户会话 | 登录状态、Token 相关 |
| **Agent 记忆** | LangGraph checkpointer（`RedisSaver`）跨进程状态持久化 |
| 限流计数 | 实时计数（应用层未启用中间件，限流在 Nginx 层） |
| 实时统计 | 在线状态、任务队列 |

### 5.2 连接参数（`app/core/config.py`）

| 参数 | 默认值 |
|---|---|

| `REDIS_DB` | 0 |
| `REDIS_MAX_CONNECTIONS` | 50 |
| `REDIS_SOCKET_TIMEOUT` | 30 |
| `REDIS_SOCKET_CONNECT_TIMEOUT` | 10 |
| 持久化 | `redis-server --appendonly yes`（AOF） |

### 5.3 客户端封装（`RedisService`）

支持数据类型与方法：

| 类型 | 方法 | 序列化 |
|---|---|---|
| String | `get` / `set(expire)` / `delete` / `exists` / `expire` / `ttl` / `incr` / `decr` | 自动 JSON |
| Hash | `hset` / `hget` / `hgetall` / `hdel` | 自动 JSON |
| List | `lpush` / `rpush` / `lpop` / `rpop` / `llen` / `lrange` | 自动 JSON |

**健壮性设计**：`init_redis()` 3 次重试 + 指数退避（`sleep(1 + attempt)`），失败后置 `None` 并**允许应用继续启动**（Redis 不可用不阻塞系统）。

### 5.4 降级策略

| 场景 | 降级行为 |

| RedisSaver 不可用 | LangGraph checkpointer 降级为 `MemorySaver`（进程内） |
| 缓存未命中 | 回源数据库 |

## 七、四库协同设计

### 7.1 数据流转全景

```
【简历入库链路】
简历文件 ──┬─→ MinIO (resumes bucket) + media/ 本地副本
           └─→ PyMuPDF / python-docx / pytesseract 文本抽取
                    ↓
           resume_parser_agent (LangGraph 5 节点) + Ollama qwen3
                    ├─→ MySQL: talents 表建档
                    └─→ bge-m3 embedding
                             ↓
                    Milvus: talent_resume 集合

【知识库链路】
知识文档 ─→ 分块（Jieba / Metadata 策略）
              ├─→ MySQL: knowledge_files + knowledge_chunks
              └─→ bge-m3 → Milvus: knowledge_base 集合

【检索问答链路】
用户提问 ─→ bge-m3 embedding ─→ Milvus COSINE 检索（ef=64）
                                    ↓
                          RBAC 权限过滤（permission_level）
                                    ↓
                          MySQL 取文档元数据 ─→ LLM 生成 ─→ 答案 + 来源

【分析链路】
MySQL 业务数据 ─→ 异步同步 ─→ PostgreSQL analytics schema
                                    ↓
                    dashboard 聚合查询 / Vanna NL2SQL 复杂分析

【Agent 状态链路】
LangGraph 执行 ─→ RedisSaver checkpointer ─→ Redis（thread_id 隔离）
```

### 7.2 一致性策略

| 关系 | 一致性模型 | 保障措施 |
|---|---|---|
| MySQL ↔ Milvus | **最终一致** | MySQL 为主数据源；向量写入失败不阻塞建档（`is_parsed` / `embedding_status` 记录状态，可重试） |
| MySQL ↔ PostgreSQL | 最终一致（异步） | 分析库由业务侧写入宽表，不参与事务 |
| MySQL ↔ Redis | 弱一致 | Redis 仅缓存可重建数据，**不作为唯一真源** |
| Redis 数据丢失 | — | 对业务无影响（可重建），AOF 提供持久化 |

### 7.3 事务边界

| 事务范围 | 说明 |
|---|---|
| 单库事务 | 各业务操作在 MySQL 单库事务内完成（`autocommit=False`，请求级会话） |
| 跨库操作 | **不入事务**：向量写入、分析库写入、缓存写入均为事务外操作，失败不阻断主流程 |
| 幂等性保障 | 联合唯一索引（`match_records` / `assessment_results` / `learning_records`）防止重复写入 |
| 级联删除 | 关联表 FK `ondelete="CASCADE"`；`talents.department_id` 为 `SET NULL` |

### 7.4 中间件不可用时的降级矩阵

| 中间件 | 不可用时的行为 | 影响 |
|---|---|---|
| MySQL | 应用无法提供业务功能 | **致命**，必须可用 |
| PostgreSQL | 分析类接口报错 | 中，不影响主业务 |
| Redis | 缓存失效、Agent 记忆降级 MemorySaver | 低 |
| Milvus | 语义检索返回空、向量写入跳过 | 中，降级为结构化检索 |
| Ollama | 简历解析/报告生成降级到 SiliconFlow 或失败 | 中，**建档门禁不阻断** |
| Dify | 抛 `DifyUnavailable`，降级本地 LLM | 低 |
