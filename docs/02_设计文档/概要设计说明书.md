## 一、系统定位与设计目标

### 1.1 系统定位

企业级 AI 原生数字化人才智能平台。以**大模型 AI Agent 为核心、RAG 知识库为数据底座、AI 工作流编排为业务驱动、自然语言数据分析为决策输出**，实现人才管理全流程智能化。

### 1.2 设计目标

| 目标 | 设计对策 |
|---|---|
| 高可用 | 各层解耦、中间件连接降级不阻塞启动、AI 能力故障时优雅降级 |
| 高并发 | FastAPI 全异步 + 多 worker + 连接池 + Redis 缓存 |
| 可扩展 | 分层架构 + 独立路由模块 + 适配器模式预留第三方对接 |
| 可迁移 | 全 ORM，禁止裸 SQL；配置外置 `.env` |
| 数据安全 | 四库分职责、行级/字段级权限、AI 能力继承用户权限 |
| 国产化 | 开源兼容栈 + arm64 多架构镜像构建能力 |

## 四、四库混合存储架构设计

### 4.1 存储职责划分

| 数据库 | 版本 | 存储内容 | 承载能力 | 实测规模 |
|---|---|---|---|---|
| **MySQL** | 8.0 | 组织架构、用户账号、角色权限、岗位信息、人才档案主数据、测评、培训、知识文件元数据、审计日志 | 高频读写事务型 | **21 张表** |
| **PostgreSQL** | 15 | 人才年度台账、测评历史、培训轨迹、行为时序数据 | 复杂统计、多维分析、分区 | **4 张表**（`analytics` schema） |
| **Milvus** | 2.4.0 | 人才简历向量、岗位需求向量、制度知识库向量 | 语义检索、RAG、智能匹配 | **3 个集合**，dim=1024 |
| **Redis** | 7 | 热点数据缓存、用户会话、Agent 记忆片段、限流计数、实时统计 | KV / Hash / List / Set | — |
| **MinIO** | — | 简历文件、知识文档对象存储（宿主机 9100 API / 9101 Console） | 对象存储 | bucket: `resumes` |

### 4.2 数据流向

```
简历上传 ─→ MinIO 持久化 + media/ 本地副本
              ↓
        PyMuPDF/pytesseract 文本抽取
              ↓
        resume_parser_agent (LangGraph 5 节点) ─→ Ollama qwen3 抽取结构化字段
              ↓                                        ↓
        MySQL talents 表（建档）              bge-m3 embedding（dim=1024）
                                                     ↓
                                        Milvus talent_resume 集合

知识文档上传 ─→ 分块策略（Jieba/Metadata）─→ bge-m3 ─→ Milvus knowledge_base
                                                           ↓
                                              检索（COSINE，ef=64）→ RBAC 权限过滤 → LLM 生成
```

### 4.3 一致性策略

| 场景 | 策略 |
|---|---|
| MySQL ↔ Milvus | 最终一致。MySQL 为主数据源；向量写入失败不阻塞建档（记录 `is_parsed`/`embedding_status`） |
| MySQL ↔ PostgreSQL | 分析库通过初始化脚本建表，由业务侧异步写入宽表 |
| 缓存一致性 | Redis 仅缓存可重建数据，不作为唯一真源 |
| 中间件不可用 | **降级不阻塞**：Redis 3 次重试后置 `None`；Milvus 初始化失败仅告警允许应用启动 |

## 五、关键设计决策（ADR）

| 编号 | 决策 | 备选方案 | 理由 | 状态 |
|---|---|---|---|---|
| ADR-001 | 采用**分层单体**而非微服务拆分 | 微服务 | 7 天工期约束下，分层单体部署运维成本最低；层间已解耦，后续可按层拆服务 | 已采纳 |
| ADR-002 | LangGraph 工作流采用**全同步**实现 | 异步 async graph | 与现有同步 DB 会话一致，避免异步会话与线程池混用导致的问题 | 已采纳 |
| ADR-003 | Agent 状态持久化优先 **RedisSaver**，降级 **MemorySaver** | 仅 SQLite | 生产需跨进程持久化；开发环境零额外依赖 | 已采纳 |
| ADR-004 | LLM 策略双通道：**ollama（默认）/ silicon_flow** | 单通道 | 本地推理保证数据不出域；高精度任务（简历解析/NL2SQL）可切云端 | 已采纳 |
| ADR-005 | Dify 定位为 **AI 中台，不承载核心业务编排** | Dify 承载全部 Agent | 避免核心链路强依赖外部中台可用性；Dify 故障时可降级本地 LLM | 已采纳 |
| ADR-006 | 密码哈希 **bcrypt cost=11** | cost=12 | cost12 登录中位 2.6s 不可接受；cost11 仍满足 OWASP ≥10，吞吐提升 30–45% | 已采纳 |
| ADR-007 | **不注册应用层限流中间件**，限流下沉至 Nginx | 应用层 RateLimitMiddleware | 网关层限流即可保护后端；精简中间件栈 | 已采纳（**限流能力在网关层，非应用层**） |
| ADR-008 | 异常体系保留**双层**（旧 `AppException` + 新 `BaseAPIException`） | 统一为新层 | 保证既有端点不回归；新端点走标准 `{code, message, details}` | 已采纳 |
| ADR-009 | 敏感字段脱敏在**服务端出参前**完成 | 前端脱敏 | 不信任客户端，前端拿不到明文 | 已采纳 |
| ADR-010 | 简历建档门禁为 **姓名 + 手机号**（降级不阻断） | 全字段校验 | AI 增强（标签/画像）失败不应阻断建档 | 已采纳 |
| ADR-011 | 国产化采用**方案 A（轻）**：开源兼容栈 + arm64 镜像 | 达梦/金仓全量替换 | 工期与风险平衡；全量替换列二期 | 已采纳（须甲方确认） |
| ADR-012 | LLM 报告生成时**关闭 qwen3 thinking** | 保留 thinking | 响应从 18s 降至约 5s | 已采纳 |

## 六、安全架构设计

### 6.1 三层权限模型（实测实现）

```
第一层：认证
  JWT（HS256，access 30min / refresh 7天，sub 强制字符串）
  ↓
第二层：功能权限（RBAC）
  33 个权限码 → 4 个角色矩阵 → require_permission_or_403() 依赖
  超级管理员 is_superuser 短路放行
  fail-closed：权限表未 seed 时，非超级管理员一律拒绝（最小权限原则）
  ↓
第三层：数据权限
  ├─ 字段级：5 类敏感字段脱敏（手机/身份证/邮箱/住址/薪酬）
  └─ 行级：data_permissions.data_scope（all / department / subordinate / custom）
           当前：super_admin/admin/hr = all，user = department；seed_rbac() 以代码矩阵为唯一事实源
           + 员工自助隔离（非 staff 用户仅见 talent.user_id == self.id）
```

### 6.2 安全机制清单

| 机制 | 实现位置 | 说明 |
|---|---|---|
| 密码哈希 | `passlib[bcrypt]` | cost=11 |
| 账号锁定 | `users.failed_login_count` + `locked_until` | 异常登录预警 |
| JWT 鉴权 | `app/utils/jwt_handler.py` | 全局依赖 |
| RBAC | `app/core/rbac.py` | 33 权限码 |
| 字段脱敏 | `SENSITIVE_FIELD_RULES` | 服务端完成 |
| 行级过滤 | `apply_talent_data_scope()` | 注入 query |
| SQL 注入防护 | `vanna_adapter`：AST 解析 + 表/字段白名单 + 禁写操作 + LIMIT 1000 | NL2SQL 专用 |
| 操作审计 | `audit_logs` 表（20 字段，含 IP/UA/耗时/结果） | 全程留痕 |
| 日志防篡改 | 审计日志设计为永久留存 | — |
| 异常不泄露 | 全局异常处理器：堆栈只进日志，**无论 DEBUG 均不回传客户端** | `main.py` |
| 传输加密 | Nginx HTTPS | — |
| 自助注册默认关闭 | `ALLOW_SELF_REGISTER=false` | 账号由管理员创建 |

### 6.3 网关层安全（Nginx）

| 配置 | 值 |
|---|---|
| 大文件上传 | `client_max_body_size 50m` |
| 请求缓冲 | `proxy_request_buffering off` |
| 超时 | `proxy_read_timeout 300s` / `proxy_send_timeout 300s` |
| 反向代理 | upstream `backend:8000`，keepalive 32 |
| SPA 回退 | `try_files $uri $uri/ /index.html` |

## 八、启动与初始化流程设计

应用采用 FastAPI `lifespan` 生命周期管理，启动顺序设计如下：

```
1. 创建必要目录（MEDIA_ROOT / logs）
2. init_db()            → MySQL 同步/异步引擎 + PgSQL 异步引擎（延迟初始化）
3. init_redis()         → 3 次重试，失败降级为 None 但不阻塞启动
4. init_milvus()        → 连接 + 确保 3 个集合存在；失败仅告警
5. init_pgsql_tables()  → 分析库 4 张表
6. init_seed_data()     → 默认组织 + 4 角色 + 超管账号 admin/admin123
   └─ seed_rbac()       → 幂等写入 33 权限码 + 角色权限矩阵 + 数据范围
7. 输出启动日志
────────────────
关闭时：close_db() → close_redis()
```

**设计要点**：中间件连接失败**不阻塞应用启动**，保证"数据库晚于应用就绪"时系统仍能起来并在后续重试。这是针对容器编排启动顺序不确定性的关键健壮性设计。

### 8.1 日志设计

| 项 | 设计 |
|---|---|
| 输出 | StreamHandler + RotatingFileHandler（单文件 10MB，保留 5 个备份） |
| 格式 | `%(asctime)s - %(name)s - %(levelname)s - %(message)s` |
| Windows 多进程安全 | 自定义 `_ShareDeleteRotatingFileHandler`，通过 `CreateFileW` 声明 `FILE_SHARE_DELETE`，规避 uvicorn 热重载下日志轮转 `PermissionError [WinError 32]` |

## 九、异常处理体系设计

系统采用**三层异常体系**，并存以保证兼容性：

| 层次 | 异常类 | 响应格式 | 适用 |
|---|---|---|---|
| 新层 | `BaseAPIException` | `{code, message, details}` | 新端点，参考统一架构 |
| 新层 | `RAGException` | `{code, message}`，HTTP 500 | 轻量域异常 |
| 旧层 | `AppException` | `{code, message, details}` | 既有端点，向后兼容 |
| 兜底 | `Exception` | `{code:500, message:"服务器内部错误"}` | 全局兜底，**堆栈不回传** |

异常类清单：参考 `app/exceptions/`（18 类 HTTP 异常 + 6 类业务域异常，见详细设计说明书）。
