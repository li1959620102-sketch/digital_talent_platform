## 二、基础设施层详细设计

### 2.1 配置管理（`app/core/config.py`）

| 设计点 | 实现 |

### 2.2 数据库连接管理（`app/core/database.py`）

**延迟初始化设计**（关键）：引擎在首次调用时才创建，且当环境变量 `TESTING` 存在时**不创建引擎**，使单元测试可在无 DB 环境下运行。

```python
_mysql_engine / _mysql_async_engine / _postgres_async_engine = None  # 模块级单例
def get_mysql_engine():
    if _mysql_engine is None and not os.getenv('TESTING'):
        _mysql_engine = create_engine(..., pool_size=20, max_overflow=10,
                                      pool_pre_ping=True, pool_recycle=3600)
    return _mysql_engine
```

**连接池参数**：`pool_size=20`、`max_overflow=10`、`pool_pre_ping=True`（防连接失效）、`pool_recycle=3600`（1 小时回收）、`poolclass=QueuePool`。

**依赖注入会话**：

| 函数 | 类型 | 用途 |
|---|---|---|
| `get_mysql_session()` | 同步 yield | 全项目主用 |
| `get_mysql_async_session()` | 异步 | 异步场景 |
| `get_postgres_async_session()` | 异步 | 分析库 |

**Base 声明**：`Base = declarative_base()`，21 张表全部继承。

### 2.3 Redis 客户端（`app/core/redis_client.py`）

**健壮性设计**：`init_redis()` 采用 **3 次重试 + 指数退避**（`sleep(1 + attempt)`），每次失败先关闭旧连接；3 次均失败后置 `redis_client = None` 并**允许应用继续启动**。

**RedisService 封装方法**：

| 类别 | 方法 |
|---|---|
| 字符串 | `get` / `set`（支持 `expire`）/ `delete` / `exists` / `expire` / `ttl` / `incr` / `decr` |
| 哈希 | `hset` / `hget` / `hgetall` / `hdel` |
| 列表 | `lpush` / `rpush` / `lpop` / `rpop` / `llen` / `lrange` |
| 集合 | `sadd` / `smembers` / `sismember` / `srem` |

**设计要点**：`set` / `hset` / `lpush` / `rpush` 对 `dict`/`list` 自动 `json.dumps(ensure_ascii=False)`；`get` / `hget` / `lpop` / `rpop` 自动尝试 `json.loads`，失败则返回原字符串。

### 2.4 Milvus 客户端（`app/core/milvus_client.py`）

**集合创建**：`init_milvus()` 在启动时调用 3 个集合创建函数，每个函数先 `utility.has_collection()` 判断，存在则跳过（幂等）。

**MilvusService 类设计**：

| 方法 | 健壮性设计 |
|---|---|
| `__init__` | **懒连接**：检查 `connections.has_connection(alias)`，未连接则补建，规避启动时 Milvus 未就绪导致后续 search 抛 `ConnectionNotExistException` |
| `ensure_schema(required_fields)` | 对比 `describe_collection` 字段集合，缺失则告警（避免 schema 漂移导致 insert/search **静默失败**） |
| `insert(embeddings, metadata_list)` | **批量 3 次重试**（间隔 1s）→ 全失败则**降级逐条插入**；成功后 `flush()` |
| `search(query_embedding, top_k, expr, output_fields)` | `load()` **重试 3 次**（间隔 0.5s）→ `search_params = {"metric_type":"COSINE","params":{"ef":64}}`；兼容 PyMilvus 2.x `hit.entity.fields` 与 3.x `hit.fields` |
| `query(expr, ...)` | `load()` 后标量查询 |
| `delete(expr)` | 删除后 flush，返回 `delete_count` |
| `count()` | `flush()` + `num_entities`，异常保护返回 0 |
| `load()` / `release()` | 集合内存加载/释放 |

**关键实现约束**：`insert()` 内部已将 `embeddings` 作为第一列拼入 `entities`，因此调用方传入的 `metadata_list` 中**不得再包含 `embedding` 字段**，否则列数多 1 抛 `DataNotMatchException`（该约束已在 `vector_search_service.py` 中以注释形式固化）。

### 2.5 LLM 工厂（`app/core/llm_factory.py`）

```python
get_llm_by_strategy(strategy=None, model=None, temperature=0.1, **kwargs)
  ├─ strategy == "silicon_flow" → ChatOpenAI(api_key=SILICON_FLOW_API_KEY,
  │                                base_url=SILICON_FLOW_BASE_URL,
  │                                model=DeepSeek-V4-Flash)
  └─ 默认                        → ChatOllama(base_url=OLLAMA_BASE_URL,
                                   model=qwen3:1.7b, temperature=0.1)
```

**设计要点**：
- `SILICON_FLOW_API_KEY` 未配置时**抛 `ValueError`**（快速失败，避免静默走错通道）；
- 阿里百炼分支已于 2026-09-02 **注释停用**（原因：Dify 五大智能体全部使用 workflow 模式，LLM 在 Dify 控制台配置，本项目代码不直接调 LLM），原始字段定义保留备查便于回滚；
- 提供专用获取器：`get_silicon_flow_llm()`（简历解析/NL2SQL 高精度）、`get_ollama_llm()`（降级兜底）。

## 三、权限体系详细设计（`app/core/rbac.py`）

### 3.1 设计目标

提供四层能力：认证层、功能权限（RBAC）、字段级权限、行级权限（数据范围）。

**三条设计原则**：
1. **fail-safe**：权限表未 seed 时（`permissions` 表 0 条记录），已认证用户不被误杀，仅匿名被挡——避免"加了鉴权导致全站不可用"；
2. **幂等**：`seed_rbac()` 可重复执行不产生重复记录；
3. **不信任客户端**：所有脱敏在服务端出参前完成。

### 3.2 权限码定义（33 个，实测）

| 分组 | 权限码 | 数量 |
|---|---|---|
| 人才档案 | `talent:view` `talent:create` `talent:update` `talent:delete` `talent:import` `talent:export` `talent:tag` `talent:parse_resume` | 8 |
| 数据看板 | `dashboard:view` | 1 |
| 用户管理 | `user:view` `user:create` `user:update` `user:delete` | 4 |
| 岗位 | `position:view` `position:manage` | 2 |
| 测评 | `assessment:view` `assessment:manage` | 2 |
| 培训 | `training:view` `training:manage` | 2 |
| 匹配 | `matching:view` `matching:execute` | 2 |
| 知识库 | `knowledge:view` `knowledge:manage` | 2 |
| 智能体 | `agent:execute` | 1 |
| 技能编排 | `skill:view` `skill:manage` | 2 |
| **字段级** | `field:talent:phone` `field:talent:id_card` `field:talent:email` `field:talent:address` `field:talent:salary` | 5 |
| **行级** | `data:scope:all` `data:scope:department` | 2 |
| | **合计** | **33** |

### 3.3 角色-权限矩阵

| 角色 | 权限特征 | 关键限制 |
|---|---|---|
| `super_admin` | 全部 33 个权限码 | 无（`is_superuser` 短路放行） |
| `admin` | 业务全权 + 5 个字段级权限 + `data:scope:all` | 无 |
| `hr` | 人才增删改、标签、导入导出、简历解析、测评管理、匹配执行 | **无 `talent:delete`（不可删档案）；字段级仅 phone + email（不可见身份证/住址/薪酬）** |
| `user` | **最小权限**：仅 `knowledge:view`（1 个权限）+ `data:scope:department` | 无任何字段级权限（全字段脱敏）；无人才/岗位/测评/培训/看板任何操作权限 |

### 3.4 核心函数设计

| 函数 | 设计说明 |
|---|---|
| `seed_rbac(db)` | 幂等写入：① 33 个 `Permission` 定义；② `RolePermission` 关联（**以代码中的权限矩阵为唯一事实源，同步撤销系统角色历史遗留的多余授权**）；③ `DataPermission` 数据范围。返回新建数统计 |
| `get_user_role_codes(user)` | 读取用户角色编码集合；异常返回空集（防御性） |
| `get_user_permission_codes(user)` | `is_superuser` 直接返回全量；否则 JOIN 查询；查询异常时**退回角色矩阵** `ROLE_PERMISSIONS` |
| `user_has_permission(user, code, db)` | `is_superuser` → True；**若 `permissions` 表总数为 0 → 拒绝（fail-closed，最小权限原则）**；否则查权限码集合 |
| `require_permission_or_403(code)` | 返回 FastAPI 依赖：内部依赖 `get_current_user`（匿名→401）+ `get_mysql_session`；无权限抛 403 |

### 3.5 字段级脱敏设计

| 字段 | 脱敏规则 | 示例 |
|---|---|---|
| `phone` | 保留前 3 + 后 4 | `13807550007` → `138****0007` |
| `id_card` | 保留前 6 + 后 4 | 中间打码 |
| `email` | 本地部分首字符 + 打码（最多 7 星）+ 完整域名 | `linshufen@tencent.com` → `l*******@tencent.com` |
| `address` | 保留前 6 字符（省市），其余打码（最多 12 星） | — |
| `expected_salary_min/max` | **直接置 `None`** | 薪酬不可见 |

**函数**：`apply_field_masking(data, user, db)`（单条）、`mask_talent_list(items, user, db)`（列表批量）。对 `pydantic` 模型先 `model_dump(mode="json")`，对 dict 直接复制；空值跳过；`is_superuser` 或有对应权限码则跳过脱敏。

### 3.6 行级权限设计

`build_talent_scope_predicate(user, db)` 构造 SQLAlchemy 过滤表达式，逻辑优先级：

```
① 员工自助隔离（最高优先级）
   非 staff 用户（角色不在 {super_admin, admin, hr} 且非超管）
   → 强制 filter: Talent.user_id == user.id
   （杜绝普通用户绕过前端直读 HR 全局人才池）

② 数据范围过滤
   scope = get_data_scope(user, db, "talent")   # all / department / subordinate / custom
   scope == "department" → filter: Talent.department_id == user.organization_id
                          若 user.organization_id 为 None → filter: Talent.id IS NULL（看不到任何数据）
   scope == "all"        → 不过滤，返回 None
   其它                  → 不过滤（fail-safe）
```

`get_data_scope()` 优先级：**用户级 `data_permissions` > 角色级 > 默认 `all`**。

**当前配置（2026-10-14 起）**：`ROLE_DATA_SCOPE` 中 `super_admin` / `admin` / `hr` 为 `"all"`，**`user` 为 `"department"`** —— 普通用户按部门隔离，遵循最小权限原则；若其组织关系缺失则查询结果为空（宁少不多）。此项由 RBAC 安全回归用例固化（`test_regular_user_uses_least_privilege_matrix`）。

> **配套前提**：部门级过滤依赖 `talents.department_id` 有值。历史业务数据中该字段大量为 NULL，因此需通过 `scripts/generate_scale_data.py` 或业务导入补齐部门归属，普通用户才能看到本部门数据（见《向量库与数据库设计》DB-01/DB-02）。

## 四、认证模块详细设计（`app/api/v1/auth.py` + `app/utils/jwt_handler.py`）

### 4.1 登录流程

```
POST /api/v1/auth/login  {username, password}
  │
  ├─ 1. 查询 User（by username）
  ├─ 2. 校验账号状态（active/inactive/locked/deleted）
  ├─ 3. 检查 locked_until 是否仍在锁定期
  ├─ 4. bcrypt 密码校验 —— run_in_threadpool 卸载（避免同步 CPU 密集操作阻塞事件循环）
  ├─ 5. 成功：更新 last_login_time / last_login_ip / login_count，重置 failed_login_count
  │      失败：failed_login_count +1，达阈值设置 locked_until
  ├─ 6. 签发 access_token（30min）+ refresh_token（7天）
  └─ 7. 写审计日志
```

### 4.2 JWT 设计要点（实测修复项）

| 设计点 | 说明 |
|---|---|
| `sub` 必须为字符串 | JWT 规范要求；历史 BUG 已修复（否则鉴权全链路失败） |
| `current_user` 为 ORM 对象 | 历史为 dict，导致端点 `current_user.xxx` 属性访问失败；已统一为 ORM 对象 |
| 算法 | HS256，`SECRET_KEY` 生产须替换为强随机串 |
| 登出 | 记录审计日志（无状态 token 的失效依赖有效期） |
| 注册 | 受 `ALLOW_SELF_REGISTER` 控制，默认 `false`（账号由管理员创建，避免绕过 RBAC 第一道门） |

### 5.2 简历解析流程（`POST /talents/parse-resume`）

```
1. 接收 UploadFile（PDF/Word/图片）
2. 保存至 media/ 并同步 MinIO（bucket: resumes）
3. 文本抽取：
   - PDF  → PyMuPDF（import pymupdf as fitz）
   - Word → python-docx
   - 图片 → pytesseract OCR
4. resume_parser_agent（LangGraph 5 节点工作流）：
   - 节点1 文本预处理与清洗
   - 节点2 LLM 结构化字段抽取（qwen3:1.7b，extract_json 剥离 JSON 围栏）
   - 节点3 字段标准化（性别/学历枚举映射）
   - 节点4 标签生成 + 人才画像生成
   - 节点5 异常数据纠错与字段补全
5. 查重（按 phone / name）
6. 建档：写入 talents 表，返回 created_talent_id
7. 异步：bge-m3 向量化 → Milvus talent_resume 集合
```

**关键设计决策**：
- **建档门禁 = 姓名 + 手机号**（降级不阻断）：AI 增强（标签/画像）失败仍建档，避免因 LLM 不可用导致主流程失败；
- `import pymupdf as fitz`：旧 API `import fitz` 在 uvicorn 下 `fitz.open()` 抛 `[Errno 22]`，已修复（修复后简历解析 API 端到端字段精度 6/6=100%）；
- JSON 抽取健壮性：`extract_json()` 处理 qwen3 输出中的 JSON 代码围栏。

### 5.3 批量导入与数据迁移（`POST /talents/batch-import` + `migration_service`）

**流程**：`上传 Excel/CSV → openpyxl/csv 解析 → 字段标准化 → 查重 → 入库 → 生成迁移报告 JSON`

**清洗规则（实测）**：

| 规则 | 说明 |
|---|---|
| 性别归一 | `男/M/male/1` → `MALE`；`女/F/female/2` → `FEMALE` |
| 学历映射 | `大专/本科/硕士/博士` → 对应 `EducationLevel` 枚举值 |
| 必填校验 | `name` + `phone` 为最低门槛 |
| 异常行处理 | 缺必填/格式错误行计入 `failed`，错误原因写入报告 `errors[:20]` |
| 去重 | 按 `phone` / `name` 判重，重复跳过并计入 `failed` |

**迁移报告结构**：

```json
{ "total": 2, "success": 2, "failed": 0, "errors": [],
  "started_at": "...", "finished_at": "..." }
```

落盘至 `backend/migrations/migration_YYYYMMDD_HHMMSS.json`。

## 六、岗位匹配算法详细设计（`app/api/v1/matching.py`）

> **重要说明**：本节为**代码实测**结果。`docs/knowledge_base/03_岗位匹配算法原理与调优.md` 描述的"技能 60 分 / 学历 5 分 / 向量 25 分"与代码不符，**以本节为准**（见《交付文档总览》D-03）。

### 6.1 算法总览

`compute_match_score(talent, position) -> Dict` —— **硬条件门槛 + 三段加权 + 经验加成**，满分为 100。

```
输入: Talent 对象 + JobPosition 对象
  ↓
[Step1] 学历门槛（权重 30）—— 不满足直接返回 0 分
  ↓
[Step2] 经验评分（权重 25）—— 不满足按比例给分
  ↓
[Step3] 技能重叠（权重 45）—— 覆盖率线性计分
  ↓
[Step4] 经验加成（上限 10）—— min(10, 工作年限 × 0.3)
  ↓
[输出] score = round(min(100, 总分), 2)
        + reasons / strengths / weaknesses
```

### 6.2 各阶段详述

**Step1 · 学历门槛（30 分，硬门槛）**

学历序：`EDU_ORDER = ["高中", "大专", "本科", "硕士", "博士"]`，`_edu_index()` 取索引；非标准值返回 `len(EDU_ORDER)`（排最后）。

```
若岗位设置了 education_requirement：
    若 talent_edu_idx >= req_edu_idx：
        score += 30；strengths += "学历匹配（X）"
    否则：
        reasons += "学历不满足要求"；weaknesses += "学历不足（要求X）"
        → 立即 return {"score": 0.0, ...}     # 硬门槛，不进入后续计算
若岗位未设置学历要求：跳过本步（不加分也不拦截）
```

> **测试提示**：匹配结果为 0 分时，**首先检查人才学历是否低于岗位要求**。

**Step2 · 经验评分（25 分）**

```
req_exp = position.experience_requirement or 0
talent_exp = talent.experience_years or 0

若 req_exp > 0：
    若 talent_exp >= req_exp：score += 25（此处分档，超出部分在 Step4 另行加成）
    若 0 < talent_exp < req_exp：score += round(25 × (talent_exp / req_exp), 1)
                                  weaknesses += "经验不足（X年/要求Y年）"
    若 talent_exp == 0：不加分
若 req_exp == 0：score += 25；strengths += "无经验硬性要求"
```

**Step3 · 技能重叠（45 分）**

```
技能集构建（兼容 str 与 dict 两种元素格式）：
    岗位侧：元素为 dict 时取 s.get("name") or s.get("skill") or str(s)
    人才侧：同上，并 lower().strip() 归一
重叠：overlap = req_skills_lower ∩ talent_skills
计分：
    若岗位有技能要求：score += 45 × (len(overlap) / len(req_skills))
                      strengths += "技能匹配 n/m（前3个技能名）"
                      weaknesses += "缺少技能（前3个缺失技能名，若存在）"
    若岗位无技能要求：score += 45；strengths += "无技能硬性要求"
```

**大小写不敏感 + 模糊匹配**：两侧均 `lower().strip()`，且支持 dict 元素，解决 `[{"name":"Python"}]` 与 `["Python"]` 混用的兼容问题。

> **数据质量关键点**：`talents.skills_certificates` 与 `job_positions.skill_requirements` 必须是标准 JSON 数组。若库中存为 Python 字面量字符串（单引号，如 `['Java','Spring']`），技能匹配将永远失败，表现为"所有人匹配分偏低且短板 = 整份技能列表"。

**Step4 · 经验加成（上限 10 分）**

```
若 talent_exp > 0 且 score > 0：
    exp_bonus = round(min(10, talent_exp × 0.3), 2)
    score += exp_bonus
```

示例：工作 3 年 → +0.9；10 年 → +3.0；≥34 年 → +10（封顶）。

**Step5 · 归一与截断**

```
score = round(min(100.0, score), 2)
```

### 6.3 匹配分区间参考

|---|---|---|
| ≥85 | 高度匹配 | 直接推荐面试（Golden 判定为"相关"） |
| 70–84 | 较匹配 | 推荐初筛，评估短板可否培训补齐 |
| 55–69 | 弱匹配 | 人才池储备，不推当前岗 |

### 9.1 处理链路

```
上传（POST /knowledge/upload）
  ├─ 文件落盘 media/knowledge/ + MinIO
  ├─ 写入 knowledge_files（file_code/file_type/file_size/knowledge_type/
  │                        status=uploaded/permission_level/uploader_id）

        ↓

  │    ├─ jieba_chunking_strategy —— 中文分词语义切分
  │    └─ metadata_strategy       —— 携带元数据切片
  ├─ 生成 knowledge_chunks 记录（chunk_code/chunk_index/content/vector_id/
  │                            embedding_status）
  ├─ bge-m3 embedding（dim=1024）
  ├─ 写入 Milvus knowledge_base 集合
  └─ 更新 knowledge_files.status = vectorized、chunk_count
        ↓
检索（POST /knowledge/search）
  ├─ 查询向量化 → Milvus COSINE 检索（ef=64，top_k）
  ├─ 按 permission_level 做权限过滤（检索前执行）

        ↓

  ├─ 检索上下文
  ├─ 拼接 Prompt（含来源文档标识，实现回答可溯源）
  ├─ LLM 生成（Dify 优先，故障降级本地 Ollama）
  └─ 返回答案 + 来源列表
```

### 10.2 LangGraph 通用运行时设计（`app/agents/graph_runtime.py`）

**考核强制三项能力的落地设计**：

| 能力 | 实现 |
|---|---|
| **状态持久化** | `get_checkpointer()` 线程安全懒初始化，优先级：**RedisSaver**（跨进程，生产）→ **MemorySaver**（进程内，默认）→ `None`（告警降级） |
| **人工介入** | `compile_graph(..., interrupt_before=["human_approval"])`；`HumanApproval` 类提供 `is_interrupted()` / `is_paused()` / `get_interrupt()` |
| **循环 + 重试** | `build_retry_loop_graph()` 构建带条件回环的工作流 |

**统一调用入口**：

```python
invoke_graph(graph, state, thread_id=None)
  # 注入 checkpointer 后调用 invoke 必须提供 configurable.thread_id，
  # 否则抛 "Checkpointer requires ... 'configurable' keys"
  config = {"configurable": {"thread_id": thread_id or f"agent-{uuid4().hex[:12]}"}}
```

**版本兼容设计**：`compile_graph()` 捕获 `TypeError`，若当前 LangGraph 版本不支持 `interrupt_before` / `interrupt_after`，退化为仅 checkpointer 编译并告警。

**`RetryWithHumanApprovalState` 状态字段**：`task` / `max_retries` / `attempt` / `result` / `success` / `approved` / `error` / `next`

**工作流拓扑**：

```
entry(execute) ──失败──> human_approval(interrupt 挂起) ──批准──> retry(循环)
      │ 成功                  │ 拒绝                                │
      v                       v                                    v
   success ───────────────> END ─────────────────────────────> (回到 execute)
```

**防死循环**：`max_retries` 兜底（默认 3）；`human_approval_node` 在无审批函数时默认自动批准，保证流程可闭环避免永久挂起。

| 3 | `AppException` | `{code, message, details}`，状态码取异常自带 |
| 4 | `Exception`（兜底） | `{code:500, message:"服务器内部错误", details:null}` |

**安全原则**：兜底处理器将堆栈与内部细节**只写日志、绝不回传客户端**（无论 `DEBUG` 是否为 true），避免泄露框架路径/表结构/内部实现给外部探测者。

## 十三、并发与事务设计

| 场景 | 设计 |
|---|---|
| DB 会话 | 请求级会话（`get_mysql_session` yield → finally close），`autocommit=False`、`autoflush=False` |
| 连接池 | `pool_size=20` + `max_overflow=10`，`pool_pre_ping` 防失效连接 |
| bcrypt 阻塞 | `run_in_threadpool` 卸载，事件循环不被 CPU 密集操作阻塞 |
| LangGraph checkpointer | 线程安全懒初始化（`threading.Lock` + 双检锁） |
| SkillRegistry / PipelineStore | 单例 + `threading.Lock` 双检锁 |
| Milvus 写入 | 批量 3 次重试 → 逐条降级，单条失败不中断其余 |
| 唯一性保障 | `match_records(talent_id, position_id)`、`assessment_results(talent_id, task_id)`、`learning_records(talent_id, course_id)` 均设联合唯一索引 |
| 级联删除 | 关联表 FK `ondelete="CASCADE"`；`talents.department_id` 为 `SET NULL` |
